# 轻量风险聚合与闭环治理平台 PRD

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v0.1 |
| 产品阶段 | MVP |
| 目标用户 | 企业内部安全团队、风险运营人员、业务负责人、整改人员、验证人员、审计人员 |
| 产品定位 | 聚合多个巡检平台产生的风险，形成统一、可追踪、可验证的整改闭环 |
| 暂定名称 | RiskHub（后续可调整） |

## 2. 背景与问题

企业内不同巡检平台通常以 Excel、HTML、飞书文档、多维表格或 API 等方式输出结果。这些结果在字段、风险等级、资产标识和状态定义上并不一致，导致以下问题：

- 风险分散在多个平台和文档中，无法统一查看。
- 同一风险被多个平台或多次巡检重复上报，存量被放大。
- 风险等级标准不一致，难以确定治理优先级。
- Owner、整改期限和流转过程依赖人工维护，容易遗漏。
- “已整改”缺少证据和验证，无法确认是否真正关闭。
- 无法准确统计风险趋势、整改效率、逾期情况和 SLA 达标率。
- 风险修改、降级、关闭和接受缺少完整审计记录。

本项目借鉴 DefectDojo 的风险聚合思路，但不复制其完整安全测试管理模型，而是聚焦企业内部风险接入与治理闭环，降低部署、配置和使用成本。

## 3. 产品目标

### 3.1 核心目标

1. 统一接入不同来源的巡检结果，并保留原始数据和导入记录。
2. 将不同来源的数据标准化为统一模型。
3. 自动识别重复发现，将治理动作集中到统一风险主记录。
4. 基于风险本身和资产上下文形成可解释的治理优先级。
5. 明确风险 Owner、整改期限、当前状态和下一步责任人。
6. 通过整改证据和复测验证形成可审计的闭环。
7. 提供面向管理者和执行人员的风险及效能报表。

### 3.2 MVP 成功标准

- 支持 Excel 文件和 API 两种稳定接入方式。
- 单批次 10,000 条数据可被完整处理，并给出成功、失败及跳过明细。
- 相同批次重复提交时不产生重复 Observation。
- 对具有稳定来源 ID 的风险实现确定性去重。
- 所有有效风险均能追溯到来源、导入批次和原始记录。
- 风险可以完成从待确认到已关闭的完整流程。
- 已关闭风险必须具有整改证据和验证记录。
- 所有关键字段变更和状态操作均可审计。
- 能生成存量、趋势、逾期和 SLA 四类基础报表。

### 3.3 非目标

MVP 不包含：

- 替代现有扫描器或执行主动扫描。
- 复杂漏洞情报、攻击路径或自动化暴露面分析。
- 基于大模型的自动判重或自动定级。
- 完整的项目管理、即时通信或工单系统能力。
- 复杂的跨组织多租户计费体系。
- 与所有外部平台双向同步。
- 自定义报表设计器。

## 4. 用户角色与权限

| 角色 | 主要职责 | 核心权限 |
| --- | --- | --- |
| 平台管理员 | 平台配置和用户权限维护 | 管理用户、角色、来源、字典、规则和全局配置 |
| 风险运营 | 接入、确认、定级、分派及治理跟踪 | 管理导入、风险、Owner、期限、合并拆分和报表 |
| 业务负责人 | 管理所属资产及风险 | 查看本团队数据、分派整改人、审批风险接受 |
| 整改人员 | 执行整改 | 查看分配给自己的风险、更新整改状态、提交证据 |
| 验证人员 | 复测或审核整改结果 | 接受或驳回验证、关闭或重新打开风险 |
| 审计人员 | 检查过程合规性 | 只读查看风险、证据、审批及审计日志 |

权限至少支持按业务团队和资产范围进行数据隔离。一个用户可以拥有多个角色。

## 5. 核心概念与领域模型

```text
Source
  └─ Import Batch
       └─ Raw Record
            └─ Observation ──┐
                              ├─ Canonical Finding
Asset ────────────────────────┘        ├─ Assignment / SLA
                                       ├─ Remediation
                                       ├─ Verification
                                       ├─ Risk Acceptance
                                       └─ Audit Event
```

### 5.1 Source（数据来源）

描述数据来自哪个巡检平台或人工渠道，包括来源类型、名称、负责人、连接配置、启用状态和默认字段映射。

### 5.2 Import Batch（导入批次）

表示一次文件上传或 API 提交。记录批次号、来源、提交人、开始和结束时间、文件摘要、总数、成功数、失败数、跳过数及处理状态。

### 5.3 Raw Record（原始记录）

保存来源数据的原始内容或其不可变引用，用于审计、排错和重新处理。敏感字段需要脱敏或访问控制。

### 5.4 Observation（发现实例）

表示某个来源在某次巡检中观察到的一条风险。它保留来源上下文，不直接承载整改状态。核心字段包括：

- 来源风险 ID、来源规则 ID、来源等级和来源状态。
- 标题、描述、建议、位置、证据和参考链接。
- 资产标识、首次观察时间和本次观察时间。
- 标准化结果、校验结果和原始记录引用。
- 去重指纹、匹配方式和关联的 Canonical Finding。

### 5.5 Canonical Finding（统一风险主记录）

表示平台认定的一项独立治理风险，是分级、分派、整改和报表的主要对象。核心字段包括：

- 风险编号、标题、类型、标准化描述和整改建议。
- 关联资产、统一等级、风险分数和治理优先级。
- 首次发现时间、最近发现时间、发现次数和来源数量。
- 当前状态、Owner、整改人、验证人及截止时间。
- 去重主键、规则版本和人工调整记录。

### 5.6 Asset（资产）

MVP 采用轻量资产模型，资产类型包括应用、域名/API、主机、代码仓库、云资源和其他。核心字段包括：

- 资产唯一标识、名称、类型和外部 ID。
- 所属业务系统、团队、环境和负责人。
- 重要性等级、网络暴露程度和生命周期状态。

### 5.7 Remediation 与 Verification

Remediation 保存整改说明、提交人、提交时间及证据；Verification 保存验证人、验证方式、结果、意见和时间。整改提交不等于风险关闭。

### 5.8 Risk Acceptance（风险接受）

风险接受是有期限、需审批且可审计的治理例外，不等于永久关闭。至少记录申请原因、补偿措施、申请人、审批人、生效时间、到期时间和审批意见。

## 6. 总体业务流程

```text
创建或配置来源
      ↓
上传文件 / 调用 API
      ↓
记录导入批次和原始数据
      ↓
格式校验、字段映射、数据清洗
      ↓
识别或创建资产
      ↓
生成 Observation
      ↓
稳定 ID / 指纹规则去重
      ↓
关联或创建 Canonical Finding
      ↓
统一分级、分派 Owner、计算 SLA
      ↓
整改或风险接受
      ↓
提交整改证据
      ↓
复测 / 人工验证
      ↓
关闭或驳回并重新整改
```

## 7. 功能需求

### 7.1 数据来源管理

#### FR-SRC-001 创建与维护来源

管理员或风险运营可以创建、编辑、启用和停用数据来源。来源至少包含名称、来源编码、接入类型、负责人和默认字段映射。

#### FR-SRC-002 来源模板

平台提供标准 Excel 模板和 API 字段规范。模板必须包含必填字段说明、示例和枚举值。

#### FR-SRC-003 来源配置版本

字段映射和标准化规则的修改需要保留版本，新批次使用新版本，历史批次仍可还原当时的处理配置。

### 7.2 数据接入与处理

#### FR-ING-001 Excel 导入

用户可以上传 `.xlsx` 文件。系统在正式写入前完成文件级和记录级预检，返回总数、有效数、错误数及错误原因。

#### FR-ING-002 API 接入

系统提供批量写入接口，支持调用方请求 ID 或幂等键、鉴权、限流和逐条处理结果。

#### FR-ING-003 批次追踪

每次导入必须生成唯一批次，状态包括待处理、处理中、部分成功、成功和失败。用户可以查看处理统计及错误明细。

#### FR-ING-004 幂等性

相同来源、相同幂等键的请求重复提交时不得重复创建数据。文件导入可使用文件摘要和人工确认辅助识别重复批次。

#### FR-ING-005 错误处理

单条记录错误不应导致整批失败。错误记录可下载，修正后能够作为新批次重新提交。

#### FR-ING-006 原始数据留存

系统保留原始文件或原始记录引用、文件摘要和处理日志。原始内容不可被普通用户直接修改。

### 7.3 数据标准化

#### FR-NRM-001 字段映射

不同来源字段可以映射到统一字段。MVP 支持文本、时间、枚举和简单拼接转换。

#### FR-NRM-002 等级归一化

来源等级映射为 `Critical / High / Medium / Low / Info`。无法识别的等级进入异常队列，不允许静默降为低风险。

#### FR-NRM-003 内容清洗

系统统一处理空白字符、时间格式、URL、主机名、端口、文件路径和大小写；清洗前数据仍需保留。

#### FR-NRM-004 资产识别

系统根据来源提供的资产外部 ID 或标准化定位信息关联资产。存在多个候选或无法识别时进入待确认队列。

### 7.4 去重与聚合

#### FR-DDP-001 稳定 ID 去重

优先使用 `来源 + 资产 + 来源风险ID` 匹配同一风险。

#### FR-DDP-002 指纹去重

无稳定 ID 时，按照来源类型配置字段生成指纹。默认候选字段包括资产、规则 ID、风险类型和标准化位置。

#### FR-DDP-003 去重作用域

MVP 默认在同一资产内去重。跨资产的同类问题仅做聚合展示，不自动合并治理记录。

#### FR-DDP-004 匹配解释

系统记录命中的去重规则、参与字段、规则版本和匹配时间，并在风险详情中展示。

#### FR-DDP-005 人工合并与拆分

风险运营可以合并误判为不同风险的记录，也可以拆分错误聚合的 Observation。操作必须填写原因并写入审计日志。

#### FR-DDP-006 重复出现与重新打开

已关闭风险再次被有效 Observation 命中时，系统更新最近发现时间并自动进入待确认状态，同时通知原 Owner 和风险运营。

### 7.5 分级与优先级

#### FR-RSK-001 原始等级与统一等级分离

平台同时保存来源等级和统一等级，来源数据更新不得直接覆盖人工确认后的统一等级。

#### FR-RSK-002 优先级计算

MVP 使用风险等级、资产重要性和暴露程度计算优先级。计算结果必须保留规则版本和命中详情。

#### FR-RSK-003 人工调整

授权用户可以调整统一等级或优先级，但必须填写原因。高风险降级可以配置为需要审批。

#### FR-RSK-004 重新计算

规则或资产属性变化后，管理员可以触发重新计算；系统需展示受影响范围，并保留调整前后的结果。

### 7.6 分派与 SLA

#### FR-ASG-001 自动分派

系统优先根据资产 Owner 或团队映射生成风险 Owner。无法分派的风险进入未分配队列。

#### FR-ASG-002 手工分派

风险运营和业务负责人可以修改 Owner、整改人和验证人，并填写备注。

#### FR-SLA-001 SLA 策略

管理员可以按统一等级配置整改天数。截止时间默认从风险首次进入待整改状态开始计算。

#### FR-SLA-002 提醒与升级

系统在到期前、到期日和逾期后发送通知。MVP 默认提醒节点为到期前 3 天、到期当天和逾期后每天一次；管理员可调整。

#### FR-SLA-003 重新打开策略

风险重新打开时默认沿用原 SLA 并继续累计逾期时间。必要时仅管理员可重置，且必须记录原因。

### 7.7 状态流转

MVP 状态如下：

| 状态 | 含义 | 允许的下一状态 |
| --- | --- | --- |
| 待确认 | 新风险或重新出现的风险等待研判 | 待整改、误报 |
| 待整改 | 已确认并等待整改人处理 | 整改中、风险接受申请 |
| 整改中 | 整改已开始 | 待验证、风险接受申请 |
| 待验证 | 已提交整改结果和证据 | 已关闭、整改中 |
| 已关闭 | 已完成验证 | 待确认（再次发现时） |
| 误报 | 确认不构成真实风险 | 待确认（撤销误报时） |
| 风险接受申请 | 等待业务负责人审批 | 风险已接受、待整改 |
| 风险已接受 | 在有效期内暂不整改 | 待整改（到期或撤销时） |

#### FR-WFL-001 状态约束

状态不能被任意覆盖，只能通过允许的动作进行转换。服务端必须校验操作者权限及转换前置条件。

#### FR-WFL-002 误报确认

标记误报必须填写原因。后续相同 Observation 默认提示历史误报，但 MVP 不自动忽略。

#### FR-WFL-003 状态历史

系统展示完整状态时间线，包括操作者、时间、原状态、目标状态和备注。

### 7.8 整改与验证

#### FR-REM-001 提交整改

整改人员可以填写整改说明并上传附件或外部证据链接。提交后风险进入待验证。

#### FR-REM-002 证据要求

进入待验证至少需要一条整改说明；进入已关闭至少需要一条有效证据和一次通过的验证。

#### FR-VER-001 验证通过

验证人员记录验证方式及意见后，将风险关闭并写入关闭时间。

#### FR-VER-002 验证驳回

验证不通过时必须填写原因，风险返回整改中并通知整改人。

#### FR-VER-003 验证方式

MVP 支持人工审核和外部复测结果两种方式。自动触发扫描不在 MVP 范围内。

### 7.9 风险接受

#### FR-ACC-001 提交申请

整改人或 Owner 可以提交风险接受申请，必须包含理由、补偿措施和到期时间。

#### FR-ACC-002 审批

业务负责人审批风险接受。申请人与审批人不能是同一人；审批拒绝后风险返回待整改。

#### FR-ACC-003 到期处理

风险接受到期后自动转为待整改，并通知 Owner、整改人和风险运营。

#### FR-ACC-004 接受期间再次发现

新的 Observation 仍需关联并计数，但在接受有效期内不自动改变状态；若风险等级升高，则进入待确认并通知审批人。

### 7.10 风险台账与详情

#### FR-LST-001 统一台账

列表支持按状态、等级、优先级、来源、资产、团队、Owner、整改人、时间范围、是否逾期和是否重新打开筛选。

#### FR-LST-002 搜索与导出

支持按风险编号、标题、资产名称和来源风险 ID 搜索。筛选结果可以导出为 Excel，导出行为需要审计。

#### FR-LST-003 风险详情

详情页展示风险概览、资产信息、全部 Observation、去重依据、整改与验证、风险接受、评论和审计时间线。

#### FR-LST-004 批量操作

MVP 支持批量分派 Owner、整改人和截止时间。批量降级、关闭及风险接受不在首期范围内。

### 7.11 通知

#### FR-NTF-001 通知场景

MVP 覆盖新分派、状态驳回、临期、逾期、重新打开和风险接受到期。

#### FR-NTF-002 通知渠道

平台内通知为必选；飞书机器人作为首个外部通知渠道。发送失败需记录并支持重试。

#### FR-NTF-003 防骚扰

同一风险、同一通知类型在配置窗口内聚合发送，避免重复提醒。

### 7.12 报表

#### FR-RPT-001 风险存量

展示当前有效风险总数，以及按等级、状态、团队、资产类型、来源和 Owner 的分布。

#### FR-RPT-002 趋势

按日、周或月展示新增、关闭、重新打开和净增趋势。

#### FR-RPT-003 SLA

展示到期、逾期、逾期率和 SLA 达标率，并支持按团队和等级下钻。

#### FR-RPT-004 整改效能

展示平均确认时间、平均整改时间、平均验证时间、风险年龄分布和各环节积压。

#### FR-RPT-005 数据质量

展示接入成功率、失败批次数、未识别资产数、未分配风险数、重复率和人工拆分率。

#### FR-RPT-006 统计口径

所有指标必须提供口径说明。趋势数据基于事件或历史快照计算，不能只依赖当前记录状态。

### 7.13 审计

#### FR-AUD-001 审计范围

系统记录登录、导入、导出、字段变更、状态转换、分派、等级调整、合并拆分、整改、验证、风险接受和配置修改。

#### FR-AUD-002 审计内容

审计记录包含操作者、时间、对象、操作类型、变更前后值、操作入口、请求 ID 和备注。普通用户不能修改或删除审计记录。

## 8. 页面与信息架构

MVP 建议包含以下一级入口：

1. **工作台**：我的待办、临期、逾期、待验证和风险概览。
2. **风险台账**：统一风险列表、筛选、批量分派和导出。
3. **接入中心**：来源配置、文件导入、批次记录和错误明细。
4. **资产中心**：资产列表、Owner、重要性及关联风险。
5. **报表中心**：存量、趋势、SLA、整改效能和数据质量。
6. **治理配置**：等级映射、去重规则、SLA、分派规则和通知规则。
7. **系统管理**：用户、角色、权限、字典和审计日志。

风险详情页是核心操作页面，建议使用“基本信息、发现记录、整改验证、风险接受、时间线”五个区域，避免操作分散到多个页面。

## 9. 数据规则

### 9.1 必填字段

一条 Observation 至少需要：

- 来源。
- 来源风险 ID 或足以计算指纹的字段组合。
- 标题。
- 来源等级。
- 资产外部 ID 或资产定位信息。
- 发现时间。

### 9.2 时间定义

- `observed_at`：来源实际观察到风险的时间。
- `imported_at`：数据进入平台的时间。
- `first_seen_at`：统一风险第一次被观察到的时间。
- `last_seen_at`：统一风险最近一次被观察到的时间。
- `resolved_at`：整改人员提交整改完成的时间。
- `verified_at`：验证通过并关闭的时间。

### 9.3 删除策略

- Canonical Finding、Observation 和审计记录默认不允许物理删除。
- 错误测试数据仅管理员可执行逻辑删除，并记录原因。
- 来源停用后保留历史数据。
- 原始文件保留期限应由公司数据合规策略确定。

## 10. 非功能需求

### 10.1 性能

- 常用风险列表在 100,000 条 Canonical Finding 规模下，95% 请求在 2 秒内返回。
- 单批次 10,000 条记录在 10 分钟内完成处理。
- 导入任务异步执行，不能阻塞用户页面。

### 10.2 可用性与可靠性

- MVP 目标月可用性不低于 99.5%。
- 导入、通知和报表任务支持失败重试。
- 处理任务必须可恢复，不因服务重启产生重复数据。
- 数据库需定期备份，并验证恢复流程。

### 10.3 安全

- 所有接口必须鉴权，并进行服务端权限校验。
- 凭据加密存储，日志中不得输出令牌、密码或完整敏感证据。
- 文件上传限制类型、大小和文件名，并进行恶意内容检查。
- 导出、附件下载和原始数据查看受权限控制且记录审计。
- 支持企业统一身份认证可作为 MVP+1 能力；MVP 至少支持安全的本地账户体系。

### 10.4 可观测性

- 记录 API 请求、批次处理、任务队列、通知及异常指标。
- 每个导入批次和 API 请求具有可贯穿链路的请求 ID。
- 对导入失败率、任务积压和通知失败配置告警。

### 10.5 可扩展性

- 数据适配器、分级规则、去重策略和通知渠道采用可插拔接口。
- 领域模型不能依赖某个具体扫描器的字段命名。
- API 需要版本化，避免接入方被非兼容变更影响。

## 11. 核心指标

### 11.1 产品使用指标

- 活跃风险运营人数。
- 已接入来源数和每周有效导入批次数。
- 自动分派覆盖率。
- 自动去重率及人工纠错率。
- 风险字段完整率。

### 11.2 治理效果指标

- 未分配风险率。
- 平均确认时间。
- 平均整改时间和平均验证时间。
- SLA 达标率和逾期率。
- 高危及严重风险存量。
- 风险重新打开率。
- 风险接受到期未处理数量。

指标需要区分“治理效果”和“数据接入变化”。例如新增风险上涨可能来自新接入一个来源，而非安全状况恶化。

## 12. MVP 验收标准

### 12.1 接入

- 使用标准模板导入包含有效、无效和重复记录的 Excel，批次统计及逐条结果准确。
- 使用相同幂等键重复调用 API，不创建重复 Observation。
- 导入失败记录能够下载、修正并重新提交。

### 12.2 去重

- 同一来源、同一资产和同一来源风险 ID 的记录关联到同一个 Canonical Finding。
- 关闭风险再次出现时自动转为待确认，并保留历史整改数据。
- 人工合并和拆分均可恢复正确关联，并生成审计记录。

### 12.3 闭环

- 风险可以按定义的状态机完成分派、整改、验证和关闭。
- 未提交整改说明不能进入待验证。
- 未通过验证不能进入已关闭。
- 风险接受到期后自动返回待整改。

### 12.4 权限与审计

- 用户只能访问授权团队或资产范围的数据。
- 无权限用户不能修改等级、审批风险接受或执行验证。
- 关键字段和状态变更均能在时间线和审计日志中查询。

### 12.5 报表

- 存量报表与风险列表筛选结果一致。
- 新增、关闭和重新打开趋势可追溯到对应事件。
- SLA 指标使用统一且可查看的计算口径。

## 13. 迭代规划

### 阶段 0：方案与基础建设

- 确认领域模型、状态机、权限范围和指标口径。
- 确认首批接入来源及真实样例。
- 完成技术架构、数据库和接口设计。

### 阶段 1：MVP 接入与台账

- 用户与基础权限。
- 资产、来源和导入批次。
- Excel/API 接入、标准化和错误处理。
- Observation、Canonical Finding 和确定性去重。
- 风险列表、详情和基础审计。

### 阶段 2：治理闭环

- 分级与优先级。
- Owner、SLA 和通知。
- 状态机、整改证据、验证和风险接受。
- 工作台和基础报表。

### 阶段 3：增强能力

- 飞书文档和多维表格集成。
- 外部工单双向同步。
- 相似度辅助判重和批量研判。
- 灵活审批流、订阅报表和企业统一身份认证。

## 14. 依赖与风险

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 来源数据缺少稳定 ID | 去重不准确 | 首批接入前建立来源数据契约，并提供指纹规则和人工纠错 |
| 资产标识不统一 | 无法正确分派和聚合 | 建立资产外部 ID 映射及待确认队列 |
| 状态与外部平台不一致 | 双方数据冲突 | MVP 单向接入，以本平台为治理状态主数据源 |
| Owner 数据不完整 | 风险长期无人处理 | 未分配队列、默认团队负责人和定期提醒 |
| 大量历史数据首次导入 | 存量膨胀、误判重 | 先进行预演和统计，确认规则后分批导入 |
| 风险接受被滥用 | 风险被长期搁置 | 强制审批、有效期、补偿措施和到期恢复 |
| 报表口径争议 | 管理决策失真 | 在上线前书面确认指标定义，并保留事件历史 |

## 15. 待确认事项
